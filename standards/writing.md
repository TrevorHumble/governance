# Writing

## Necessary information

Remove and don't include unnecessary information: every line is necessary and makes sense with only the context the reader has.

- Write each idea down once, in this file and every other. Link to the one home instead of copying.
- Combine related ideas.
- No opening line that restates the heading. If a section can be one line, make the section one line.

## Word choice

- Use the terms of the reader's field instead of descriptions or generic phrases: "Preview", not "What will be sent"; "Font style", not "Which weight and slant of the family the text wears".
- A description adds context and repeats no words or meaning from the label: for a Rectangle tool, "Drag to draw, click to select", not "Draw a rectangle".
- No vague filler words, such as look, some, here, keeps, already, thing, stay, own and plain: "Set dash phase to 0 to maintain appearance", not "Phase 0 keeps the look". CI bans a fixed list of words as well: run `npm run check:banned`.
- No relative clause in place of a term: "Earning points", not "How you earn points"; "Fit the page to all visible objects", not "Fit the page around everything you drew". A real question, "How to" for a set of steps, and a clause with no single-term equivalent are fine.
- No pronoun at the end of a sentence, line or label, and no pronoun without the noun in the same line: "Export selected objects with page fitted to objects", not "fitted to them". A pronoun early in a sentence, and this or that before something on screen ("Hide this warning"), are fine.

## Headings and labels

Name each title, label and heading like a label on a box: the name of the contents. "Design principles", not "Rules every card follows"; "Demos", not "See it work".

## Evidence in findings

Quote the line, the word, or the output. A finding without a quotation is not a finding.

## Names

No FINAL, LAST, or TRULY_FINAL in file names or headings. The next change makes them false. Use a version or a date.
